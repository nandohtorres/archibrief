The big ideas, explained

Read this section first. The timeline below shows when things happened — this is what they actually mean.

Terraform: the blueprint, not the builder's own power

Terraform is a contractor who only has exactly the tools you personally handed them — nothing more.

What it is .tf files describe the AWS infrastructure that should exist — a bucket, a Lambda, a database. terraform plan previews what would change; terraform apply actually makes it happen.
Why it matters Terraform has no power of its own — it acts using your AWS credentials, so it can only ever do what your own IAM permissions allow. Every "access denied" this project hit wasn't Terraform failing; it was a real, honest reflection of what the account was and wasn't allowed to do yet.

Least-privilege IAM: permissions earned, not assumed

A new employee doesn't get a master key on day one — they get access to exactly what their current job needs, and nothing else.

What it is The account used to build this project (archibrief-deploy) only has the specific AWS actions it's been explicitly granted, tracked in one policy file and pasted into the AWS console by hand.
Why it matters This is why permission errors kept showing up throughout the build: nobody pre-granted broad access "just in case." Each new capability (writing to S3 Vectors, calling Bedrock) got its permission added only once something real actually needed it — and stale permissions from designs that got cut later (like the old Cognito access) get removed once nothing uses them anymore.

RAG and chunking: giving the AI real sources to cite

Instead of asking someone to answer from memory, you hand them the specific paragraph of the manual that actually applies.

What it is RAG (Retrieval-Augmented Generation) means the system looks up real AWS documentation before forming an opinion, rather than relying on what the underlying model already "knows." Chunking is how a long document gets split into small enough pieces to search over individually.
Why it matters How you split matters as much as that you split. Splitting on real structure (headings, whole tables, a PDF's own table of contents) instead of arbitrary character counts keeps each piece meaningful on its own — a table cut in half is useless as a citation.

Embeddings and vector search: meaning as coordinates

Instead of matching exact words, it's like plotting every sentence on a map where similar ideas land near each other — then asking "what's nearby?"

What it is An embedding model (Titan V2, here) converts a chunk of text into a list of 1,024 numbers that represent its meaning. S3 Vectors stores all 24,897 of these and can find the ones closest in meaning to a new question.
Why it matters This is what lets the system find the actually-relevant AWS guidance for a question, even if the question doesn't use the exact same words as the source document. It's also the one step in this whole build that costs real money per use — every chunk has to be converted once, which is why that step got the most scrutiny before running it for real.

Why the no-accounts pivot was the right call

A demo doesn't need a working front door if the only person who'll ever walk through it is the one who built the house.

What it is Originally planned: a full login system (Cognito, passwords, email codes, roles for different users). Replaced with one private admin key for running real reviews, and a single always-public, pre-generated demo report for everyone else.
Why it matters This project's actual purpose is demonstrating engineering judgment to recruiters, not running a real multi-user product today. A login system would have proven skills already shown elsewhere in the build (IAM, security design) while adding real scope that delayed getting to a working, honest demo. Recognizing that — and cutting the half-built work rather than finishing it out of momentum — was itself the harder and more valuable decision.

The journey so far

Ten days, from a blank repo to a live AWS backend with a working RAG pipeline. Not a straight line — the pivot and the fixes below are as much the story as the features.

Sep 4

Scaffolding and the decision process

Repo created. Every non-trivial choice — language, database, auth, cost controls — got its own architecture decision record (ADR) rather than living only in chat history. That discipline is what made the pivot later possible without losing context.

Sep 4–8

Design phase

Full system design worked out: Terraform-managed AWS backend (API Gateway, Step Functions, Lambda, DynamoDB, S3 + S3 Vectors, Bedrock), a LangGraph reasoning subworkflow, and a structure-aware RAG chunking strategy. Independently reviewed for gaps before any infrastructure was built.

Sep 8–10

First real infrastructure buildout

Terraform written for the full stack and applied against a real AWS account for the first time. Took roughly ten apply attempts — each one surfacing a genuine missing permission or a real design gap, never guessed around. Full buildout went live: Cognito, API Gateway, DynamoDB, S3 + S3 Vectors, five pipeline Lambdas, Step Functions, Bedrock Guardrails.

Sep 11

The pivot: cutting user accounts entirely

Mid-build, a hard question got asked honestly: does a real login system (Cognito, MFA, signup) actually serve a portfolio project meant to demonstrate engineering skill — or is it scope that doesn't move the needle? The answer was no. Replaced entirely with one pre-shared admin credential gating the real pipeline, and a fully static, always-public guest demo. Every affected ADR, spec, and diagram was rewritten the same day rather than left to drift.

Scope cut, not deferred
Sep 11

Migrating live infrastructure to match

Cognito and its authorizer were torn down and replaced with a new admin-gated Lambda authorizer, against infrastructure that was already live — the harder version of this kind of change. Verified clean afterward with a matching Terraform plan.

Sep 11

Building the RAG pipeline

A document-normalization and chunking pipeline that splits on real document structure rather than arbitrary character counts — heading tags for HTML, and each PDF's own outline/bookmark tree for the AWS Well-Architected whitepapers, which turned out to carry genuinely accurate nested structure.

Sep 11

Real ingestion, real corpus

Ran the pipeline against all ten approved sources — six AWS Well-Architected pillar whitepapers plus four AWS security reference pages. Result: 24,897 chunks, about 11.8 million tokens, every one carrying full citation metadata back to its source.

Sep 14

Proving retrieval before trusting it

Built an 18-question evaluation set against the real ingested chunks before treating any embedding or chunking choice as final — including a couple of questions deliberately designed to be ambiguous across two different sources, to stress-test whether retrieval can actually tell them apart.

Sep 14

Catching a real bug before it cost anything

Before running the one script that spends real money — embedding ~25,000 chunks via Bedrock — it went through independent review rather than being trusted on the first pass. That review found a genuine flaw: a single failure partway through could have let almost the entire run bill anyway, and paid-for work could be lost on a crash. Fixed before a single real API call was made.

Sep 14

The run itself — twice stopped cheaply, then clean

The first real attempt stopped itself after exactly one call when AWS's own account-verification hold on Bedrock kicked in — a real, separate, one-time gate, unrelated to anything built here. It cleared within about an hour. The retry then caught one more real bug the same way: a handful of chunks with an empty heading field that S3 Vectors flatly rejects. Fixed, and the full run completed clean — all 24,897 chunks embedded in under 13 minutes, zero errors.

Sep 14

The measurement that revealed a much bigger problem

Running the 18-question eval set against the real, live index for the first time gave a recall score of 50% — technically a result, but not one to just accept at face value. An independent review of the whole pipeline, checked personally rather than trusted on its word, found something much more consequential than a mediocre embedding model: 93.5% of the entire 24,897-chunk corpus was exact-duplicate content, caused by a PDF-parsing bug that gave several headings on the same page identical, misattributed text. The 50% number was measuring a broken pipeline, not Titan's real quality.

Root cause found, not just a symptom
Sep 14

Fixing it properly before spending anything else

Three real fixes went in the same day: the PDF duplication bug itself, a gap where heading labels like "COST01-BP01" were never actually given to the embedding model at all, and a broken pattern-matching rule that silently failed to recognize the exact AWS identifiers this corpus is full of. The corpus is being re-generated from scratch against the fixed pipeline before another dollar gets spent re-embedding it.

What actually went wrong along the way

The parts worth remembering — not because they're flattering, but because they're the real engineering.

A permissions bug that wasn't a permissions bug

An AWS command kept failing with "access denied" despite every check confirming the IAM policy was correct — burned real troubleshooting time on a phantom problem.

The actual cause: a CLI profile silently defaulting to the wrong AWS region, so the request was being checked against a policy scoped to a different region entirely. Fixed, and the profile's default corrected so it can't recur.

Terraform couldn't order its own teardown

Removing the old Cognito authorizer while repointing a route that still referenced it hit a real gap in Terraform's dependency graph — it doesn't know to reorder around a resource that's been deleted from the config entirely.

Split into two sequential targeted applies instead of one, in the right order.

The scope call that was harder than the code

A real user-accounts system was half-built and technically fine — but kept raising the question of whether it actually served the project's real purpose, or was just familiar work.

Cut it entirely rather than finishing it out of momentum, and rewrote every document it touched the same day so nothing was left half-true.

A near-miss on real money

A script built to make ~25,000 paid API calls looked correct on a first read — batching was right, retries were right, tests passed. A deeper independent review found that a single mid-run failure could still let nearly all of them fire anyway, due to a non-obvious default in how Python's thread pools handle cancellation.

Verified the claim by reproducing it directly, then fixed it — bounded batches, a one-chunk smoke test first, and crash-safe checkpointing — before running anything for real.

93.5% of the corpus was duplicate content

A 50% retrieval score on the first real measurement was tempting to explain away as "the embedding model isn't great." Instead of accepting that, the whole pipeline got an independent second look — which found that a PDF-parsing detail was silently giving several different headings on the same page byte-identical text, for almost every page in six large source documents.

Personally re-verified every number before trusting it (recomputed the duplication stats directly from the real data — they matched exactly), fixed the actual root cause plus two related gaps, and re-generated the corpus from scratch rather than patch around bad data.
