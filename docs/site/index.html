ArchiBrief

A secure AWS architecture reviewer: submit a bounded Terraform repo and a workload brief, get back typed, cited, confidence-scored findings — evaluated against the AWS Well-Architected Framework and security best practices.

System diagram + full product lifecycle, step by step

1 System architecture — the pieces

What each component is and how they connect. The browser talks to Next.js directly for static assets and to Cognito directly for auth; application API calls go through API Gateway. Step Functions owns the durable job and writes to storage itself at the ingest/finalize boundaries; the AgentCore/LangGraph subworkflow reads/writes storage for retrieval and evidence during reasoning.

2 The full product lifecycle — step by step

Two separate paths, not one continuous line. A guest only ever sees a cached demo — they never run their own review or use "go deeper." Amber-ringed steps are decision points where the path branches.

Path A — Guest (no account) — cached demo only, never runs the real pipeline
G1

Land on the site, try it instantly as a guest

No signup required for a first look

In plain wordsYou show up and can immediately click "try the demo" — no account, no credit card, no waiting. You see a real, complete example report for a fixed sample project, not your own code.
TechnicallyGET /demo serves a precomputed/cached report for a fixed reference Terraform example — not a fresh pipeline run per visitor, and not connected to the full review pipeline below. Rate-limited by a salted/rotated session identifier, never a raw IP.
ADR-0010 ADR-0029 ADR-0030
G2

Prompted to create a free account

End of the guest path

In plain wordsAfter your one free guest look, you're invited — not forced — to create a free account if you want to review your own infrastructure.
TechnicallyGuestSessions.useCount tracked per salted/rotated session key, capped at one use, then prompts account creation. Accepting moves you to Path B below — a guest never runs the real pipeline or uses "go deeper" directly.
ADR-0010
Path B — Full review (real account) — your own Terraform, the actual pipeline
1

Create a real account, or log in

Required for a real review

In plain wordsYou sign up the normal way — email and password. You also get a one-time code emailed to you as an extra security step.
TechnicallyCognito user pool, email/password as the primary credential, an emailed one-time auth code as a second factor. Backend validates the Cognito access token and enforces app roles server-side — no AWS credentials issued to the browser.
Not yet decided: whether the emailed code is required on every login, only new devices, or only for sensitive actions.
ADR-0018 ADR-0043 ADR-0037 ADR-0042
2

Submit a review

Paste/upload your Terraform, describe the workload

In plain wordsYou provide your infrastructure code and a short plain-English description of what you're building and why (traffic expectations, whether it handles sensitive data, etc.).
TechnicallyPOST /reviews accepts a bounded Terraform repo reference (stored in S3) + a workload brief. Step Functions (Standard) accepts and persists the job, returns a reviewId.
ADR-0028 ADR-0034
3

Ingest — your code is read, never run

Safety boundary #1

In plain wordsThe system looks at your Terraform files as plain text/structure — it never actually executes them. That means it can't accidentally download something malicious or rack up cloud charges on your behalf.
TechnicallyLambda does a static-only HCL parse — terraform init/plan/apply/provisioners/external data sources are never executed. Rejects path traversal, archive bombs, oversized files, unsupported encodings. Bedrock Guardrails scans the workload brief for prompt-injection attempts here — this check only covers this tagged input, not the Terraform content itself or anything retrieved later.
ADR-0027 ADR-0033
4

Preflight check — is anything important missing?

Decision point — branches three ways per field

In plain wordsFor things like "do you handle regulated data?" — if the system can safely model a conservative default, it does and clearly labels every affected finding as an assumption. If it truly can't know, it says so plainly instead of pretending. If the answer genuinely matters for the review, it pauses and asks you directly for that specific field.
TechnicallyLangGraph's PreflightGate node (part of the AgentCore reasoning subworkflow, not a Lambda) evaluates each baseline data point against a per-field policy: cannot infer → marked unknown/not-observable; can model conservatively → a named, versioned default, every dependent finding tagged assumption; required → pause via a Step Functions task-token callback.
Not yet decided: which specific baseline fields fall into which of the three categories — the policy shape is locked, the field-by-field assignment isn't.
ADR-0031 ADR-0028
5

You answer specific questions (only if paused)

Optional branch — only triggers when a field is genuinely required

In plain wordsIf the system genuinely needs to know something to give you a meaningful review, it'll ask exactly what's missing — not a long intake form. If you don't answer in time, it either falls back to a safe assumption or just skips that part of the review.
TechnicallyPOST /reviews/{id}/clarify resumes the paused execution via the Step Functions task token, returning the specific missing fields the user must answer. On timeout, falls back to the "can model conservatively" default if one exists for that field, else stops just that portion of the review.
ADR-0031 ADR-0028
6

Deterministic rule checks

The fixed-checklist pass

In plain wordsThe system runs your infrastructure through a known checklist of common mistakes and best practices — is a storage bucket public when it shouldn't be, is encryption turned on, that kind of thing. This part isn't AI judgment — it's fixed, reproducible logic that gives the same answer every time on the same input.
TechnicallyLambda rule_engine runs the 10-20 v1 scenarios (IAM, exposure, encryption, availability, recovery, observability, cost) against the parsed Terraform structure.
ADR-0002 ADR-0028
7

Retrieve real evidence

Grounding — not guessing

In plain wordsBefore forming an opinion, the system looks up the actual AWS documentation and security guidance that applies to your setup — the same way you'd look something up yourself, not from memory.
TechnicallyLangGraph's Retrieve node embeds the query context using Titan V2 (the current working baseline candidate, not a finalized choice — a formal evaluation against alternatives is still planned) and searches S3 Vectors — a structure-aware-chunked index of AWS Well-Architected/security docs — returning top-k chunks with richer citation metadata than a single URL (source, edition, exact text span, content hash, among other fields).
ADR-0035 ADR-0036
8

Safety re-check before reasoning

Safety boundary #2 — narrower than it sounds

In plain wordsRight before the AI forms its conclusions, the system checks the inputs it's about to act on for manipulation attempts. This check does not cover the documents it just retrieved — those are protected a different way (see technical note).
TechnicallyBedrock Guardrails' prompt-attack detection runs again on the tagged model input at this stage — it does not inspect retrieved/tool results. Retrieved evidence is protected instead through the allowlisted, versioned RAG corpus, deterministic retrieval allowlists, provenance checks (every claim must cite retrieved evidence), and an adversarial regression test suite covering poisoned retrieved text specifically. Any experimental Hugging Face-based classifier stays an isolated shadow-evaluation path — never the production route.
ADR-0033 ADR-0038
9

AI reasoning — findings get written

The core synthesis step

In plain wordsClaude reads the checklist results and the real evidence it retrieved, then writes up findings — but every claim has to point back to something real. No finding gets to just "sound right."
TechnicallyLangGraph's Reason node (Bedrock Claude) synthesizes RuleEngine output + retrieved evidence into typed Finding objects. Lightweight-first-pass prose by default, but every required field (finding, evidence, confidence inputs, risk/impact, recommendation, framework mapping) is still populated. The model ID, prompt version, corpus version, and retrieved chunks are snapshotted with the result.
ADR-0023 ADR-0039
10

Validation

Nothing ships without proof

In plain wordsBefore a finding is allowed to reach you, the system double-checks it actually has a citation and a clear type — a finding without a source simply can't get through.
TechnicallyLambda enforces the Finding pydantic schema — a missing citation raises a pydantic validation error at this layer, not something that could silently slip through to output.
ADR-0022
11

Audit log

Traceability

In plain wordsKey facts about your review get recorded — what was assumed, what defaults were applied, what the safety checks decided — so the process can be traced back later if needed.
TechnicallyAuditLog records inputs, defaults applied, and Guardrails decisions for every execution — not a full byte-for-byte replay log, a defined, traceable record of those specific fields.
ADR-0022
12

Report assembled and delivered

The finished product

In plain wordsYou get a complete report — every recommendation cited, rated by confidence, and clearly labeled as fact, assumption, or recommendation.
TechnicallyFinalize assembles the structured HTML/JSON evidence ledger; the large payload goes to S3 with a pointer in DynamoDB (a DynamoDB item caps at 400 KB). GET /reviews/{id} returns it.
ADR-0002 ADR-0034 ADR-0039
13

Explore the findings

Reading the report

In plain wordsYou browse the results and can immediately tell what's a solid fact, what's an educated assumption, and what's a suggestion — instead of one big wall of undifferentiated text.
TechnicallyEach Finding carries an explicit type tag (fact / deterministic-rule-result / inference / assumption / recommendation / not-observable) rendered distinctly in the UI.
ADR-0002 ADR-0039
14

"Go deeper" on any one finding

Optional, on-demand branch — real accounts only

In plain wordsCurious about one specific finding? You can ask for a deeper look at just that one thing, without waiting for the whole review to run again.
TechnicallyPOST /reviews/{id}/findings/{id}/deeper re-runs Retrieve → Reason (deep mode) → Validate scoped to one findingId. The result is a versioned child of the original snapshot — never a disconnected re-run that could silently contradict it.
ADR-0039 ADR-0023
15

Admin access (Fernando only)

Not part of the normal user path — shown separately, not step 16 of the main flow

In plain wordsFernando can access an elevated view — used for recording demo videos and presentations, not something any user or recruiter gets by default. The exact scope of that view isn't designed yet, just who can have it.
Technicallyadmin role restricted to Fernando, granted through an out-of-band audited procedure — never an in-app self-service endpoint. A separate, constrained reviewer role for recruiters is planned later, not built in v1.
